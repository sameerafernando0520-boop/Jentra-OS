This supersedes the earlier `PRIVATE_PROVIDER_CONTRACT.md` statement that no transport implementation exists. The new modules implement actual HTTPS, Supabase Auth, PostgreSQL reads, a fixed Management API read bridge, fixed synthetic membership fixtures, private preparation persistence and the provider interface. Their local tests use controlled request/driver objects and actual encrypted temporary files containing synthetic identities. No real connection, sign-in, MFA factor, SQL mutation or load run was performed by this implementation task.

## Implemented paths

- `supabase_http_transport.mjs`: fixed-project HTTPS and fixed Auth/RPC routes; an independent agent per participant; request writes only after the actual socket queue, verified TLS handshake and synchronous coordinator deadline hook; bounded responses; no retries or redirects; fixed public error codes. Connection IDs identify independently held transport agents, not PostgreSQL backend IDs. Real server spans remain absent. Idle sockets are drained before trusted races and trusted connections close after known race restoration.
- Auth uses real `/auth/v1/token?grant_type=password`, `/auth/v1/user`, TOTP factor enrollment/challenge/verification, and an exact committed `auth.sessions` row. Issued claims are parsed only to locate the actual session; parsing alone supplies no authority. Tokens and factor secrets remain in private closures/callbacks. `adopt` supports an existing genuinely minted private session pool, with the same online/row/MFA checks. It never constructs a JWT or inserts an Auth row. Enrollment is an explicit private preparatory method and is not automatically invoked by the harness.
- `supabase_read_store.mjs`: a privately supplied reviewed Node PostgreSQL client; only fixed SELECTs and typed values; exact project DB/pooler target; verified TLS; fresh read-only repeatable-read transactions, real backend/snapshot identity, COMMIT and query/result hashes. The Auth query reads only id, user_id, created_at, updated_at, not_after, aal and factor_id. Root independently confirmed those installed catalog columns at 2026-10-12 09:43:42.764619 UTC. Its connected `postgres` catalog access does not make a local PostgreSQL password available.
- `supabase_management_read.mjs`: an optional fixed-project read bridge using a privately supplied genuine owner PAT and the documented Management API `database/query` route with typed `parameters` and `read_only: true`. It permits ten fixed SELECT recipes, including installed metadata, capped source counts, exact500 forecast identities and a supplied real actor/session pair. It waits for verified TLS, refuses redirects/retries/arbitrary SQL, bounds the full queue/request deadline and response, and retains actual server read-only/isolation/backend/snapshot/time metadata. It explicitly reports `committedTransactionProof: false` and `repeatableReadProof: false`; this HTTP read facility does not replace the runtime fixture contract's committed repeatable-read PostgreSQL proofs or privileged membership transaction transport. No PAT is available to this implementation task and this bridge has not contacted Supabase.
- `preparation_journal.mjs`: mandatory source-bound private evidence before each setup RPC or administrative write. It retains immutable original commands, membership/assignment baselines, transaction identities, returned invitation/proposal/revision IDs and private recovery material. Exact acknowledged record/storage hashes precede dispatch; reserved envelope fields cannot be overwritten. A failed append or uncertain operation stops later preparation, load and restoration. Waiting intent receipts recheck that stop condition before dispatch. Private invitation material never enters the public CLI journal.
- `preparation_file_sink.mjs`: an executable encrypted append-only private sink and read-only recovery reader. It copies the privately supplied32-byte key and source binding without import/constructor I/O. The first append exclusively creates a new exact outside-repository directory; every record uses a fresh AES-256-GCM nonce and an exclusive file, with actual file write/sync/close before acknowledgement. Authenticated source envelopes and chained storage hashes bind every original. Partial attempts are retained and stop later appends; existing directories, source drift, wrong keys, invalid sequence, tampering and symlink/junction paths fail closed. Recovery never dispatches or restores. Without an independently retained exact expected head, the reader reports only an available prefix with `completenessVerified: false`; an expected record count/final storage hash must match for `true`. Both paths keep `automaticReplayAllowed: false`. The acknowledgement proves a real file-content sync, not independently verified directory-entry/power-loss durability on the private Windows filesystem. The actual owner-private folder, ACL, credential-store key, trusted external head retention and host durability proof remain unconfigured and unverified.
- `supabase_membership_fixture.mjs`: exact new load-001 approver/executor memberships, original assignment IDs, guarded current versions and subscription row lock. A private original baseline is acknowledged before the first mutation; every write and COMMIT has its own acknowledged intent/result. Those callbacks recheck cancellation after any delayed receipt and immediately before SQL. Preparation suspends just those two and sets cap3 after occupancy2. Restoration raises cap4 before reactivation, preserves incremented versions and all immutable history, and revokes only this run's exact pending invitations from the reviewed billing actor to the two reviewed emails. Unknown COMMIT prevents retry or restoration. These are administrative fixture actions, separate from the authenticated race commands.
- `supabase_runtime_provider.mjs`: genuine supported Auth/HTTP RPC calls; installed signature/grant and quiescence checks; actual nonempty indexed forecasts across all500 exact scope triples; source cap checks; source-bound revision scheduling, proposal creation/independent MFA approval and exact invitation creation; accept-only subscription registration after prior forecast races; original race IDs, independent readiness, committed per-invitation/invocation/revision denial proof, before/after effects, exact restoration and load snapshots. No model/send endpoint is in the load dispatcher.

The public coordinator acknowledges `case-preparation-intent` before calling `provider.prepareRace`. That allowlisted entry retains original case/scope/fixture/preparation/restoration/query hashes and participant/send policy. A failed public journal write prevents all preparation; private returned IDs and invitation material stay in the separate encrypted journal. Local tests verify both ordering and the failed-write boundary. The timed rejection regression uses a controlled clock and requires an actual controlled denied dispatch, eliminating its former50ms host-scheduling race without changing the real load clock, duration, rate, coverage or latency thresholds.

Activation/admissions execute before quota reservations and before other runtime phases populate usage periods. Existing busy quota periods block preparation; they are never cleared. Only the exact accept subscription may be registered for lease contention; other three receiver paths are registered by the separate delivery task afterward. Previously enabled subscriptions or eligible old heads block this one-lease fixture. Known claim-only leases and quota reservations remain durable.

Revision scheduling binds the exact reviewed per-scope plan, seven-day trial interval from actual server time, current subscription version and race seats (runtime5/load-001 admission2). It rejects another existing plan or arbitrary interval/seat configuration and checks the actual stored revision against those exact values. A local draft initially used one day; no scheduling was executed, and the successor code/interval regression corrects that scope mismatch while retaining the earlier local records.

The quota before read executes the same scoped/query recipe with an empty invocation cohort because the coordinator allocates the20 original invocation IDs afterward. It requires no existing reservation rows and zero reserved/settled units. The after read checks all20 actual original IDs, including every rejected invocation. It does not pretend the20 IDs were queried before they existed.

Quota period reads return lossless PostgreSQL timestamp text. A JavaScript Date round-trip would truncate microseconds and fail the installed metering function's exact period equality. Indexed billing reads bind the returned tenant to the exact requested reviewed scope and validate the existing activation allowlist: runtime/load-001 return syntheticTarget true; the other reviewed load scopes return false. No additional allowlist rows are created. Database target/TLS settings are copied privately and revalidated for each connection so later configuration or driver buffer changes cannot redirect a dispatch.
