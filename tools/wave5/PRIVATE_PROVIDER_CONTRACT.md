# Wave 5 private runtime provider contract

This contract is for the new `tools/wave5` coordinator. It does not install or authorize anything. It references the immutable [current runtime review](../../docs/verification/wave5/complete-app-runtime-review-20261010-r5.md), bundle `db525758554036fa99ec02d00c85bd8401ef7ebce787e2a983db1c69a08baf7b`. Its 71 operations exclude the installed six. Production, real billing, existing accounts/stores and global Auth changes remain excluded.

## Trust boundary and availability

There is **no genuine private provider configured or implemented in this repository**. The coordinator has no HTTP client, service key, Auth password, JWT decoder, fabricated session, database write or native automation. Controlled tests inject local functions and virtual time; they do not implement this private provider or satisfy a runtime gate.

A separately reviewed private `.mjs` provider must reside outside this repository. Its exact source hash, dependencies/transport implementation, concrete fixture/committed query plan and private storage access must be reviewed in an addendum before execution. It must contain no embedded credentials; credential values stay in owner-authorized private storage and private memory. Its exported `createWave5PrivateProvider(context)` returns the methods below. Importing the module occurs only after the exact owner decision has passed. The provider must have no import-time network or secret access and must not log exceptions, headers, tokens, account passwords, MFA seeds/codes, invitation tokens, service keys or raw business responses.

The local coordinator can verify bindings and orchestration; it cannot make a private implementation truthful by trusting a Boolean. The provider's online Auth/session-row evidence, SQL query bytes, transport callbacks and installed-contract proofs require separate review and actual observations. A hash-bound, unreviewed provider is insufficient. Missing capacity, Auth or transport facilities remains an incomplete gate.

## Local approval and concrete plan

`run_runtime_verification.mjs` defaults to validation with zero network/private-provider calls. `--execute` requires the exact immutable runtime file/body hash, current harness review/file hashes, concrete plan file hash and private provider file hash. The public owner decision is `kind: wave5-runtime-owner-decision`, `decision: approve`, with `source.kind: direct_user_message`, its preserved message hash/reference, `approvedAt`, `projectId`, `production: false`, `realBilling: false`, `installOriginalSix: false` and `noGlobalAuthChanges: true`. It authorizes the same bounded runtime operations and persists across continuation. It is not permission for another target. Approval provenance must come from the human; a file invented by an agent cannot authorize execution.

The separate source-bound `wave5-runtime-harness-preparation` attestation binds the harness/plan/private-provider hashes and a byte-verified independent review result (`approved-for-existing-bounded-scope`), with `sameApprovedOperationScope: true`, `additionalOwnerAuthorizationRequired: false` and the same exclusions. The independent JSON must itself have kind `wave5-runtime-harness-independent-preparation-review`, the actual approved result, exact runtime bundle/file, harness/plan/private-provider hashes, current `operationScopeSha256`, `sourceBindingsVerified: true` and the same scope/exclusion fields. An attestation cannot relabel a review whose actual verdict is changes requested. The private factory receives deeply frozen copies; live entry independently revalidates the canonical bundle, semantic plan hash and review body before touching provider operations. This technical preparation does **not** demand a second owner approval for code hashes. A new human decision is necessary only if actual operations would exceed the already approved scope. Fresh contract/capacity/expiry checks remain technical runtime checks.

The public plan is `kind: wave5-runtime-harness-plan`, with the exact project/base URL/runtime bundle, `warmupMs: 60000`, `measuredMs: 300000`, `maxRunMs: 900000`, `maxInflight: 2000`, `maximumTimedRequests` at most 100000, and a capacity-reviewed request rate between 20/s and the request cap divided by 360 seconds. Default use of 200/s would dispatch 72000 requests over 360 seconds. Session population and peak simultaneous HTTP requests are reported separately; 2000 active Auth sessions does not imply 2000 simultaneous requests.

All seven cases are required, each with an original case UUID, exact fixture/preparation/restoration/committed-query hashes, scope, participant count and `noExternalSend: true`. The four invalid-boundary cases have fixed `LIMIT_EXCEEDED` expectations and concrete fixture/query hashes. Load needs its own `loadCommittedQuerySha256`, `loadFixturePlanSha256` and separately reviewed `externalObservationSourceSha256`. There is no live-ready plan included: genuine returned identities, reviewed prepared fixtures, queries, restoration, complete transport observation and capacity are still missing. A controlled plan in the test file is explicitly a local fixture and is not approval.

## Provider methods

All methods honor the supplied `AbortSignal`; timeouts stop new dispatch. Pending or uncertain mutations are preserved for review, with no automatic resubmission, release of unknown reservations or cleanup that hides an effect. `close` closes transport resources only. Methods return typed public facts plus opaque private handles only where noted; the coordinator records an explicit allowlist of public fields.

| --- | --- |

Verify current capacity/tier/hardware/row distribution and reviewed job quiescence. Return the exact fresh proof shape validated in `validatePreflight`. No installation, global Auth change or fixture seeding occurs here. |
| `openSessions({review, signal})` | Independently authenticate the already approved private actors, or obtain the separately authorized sessions from their private store. Online Auth verification and a read of each actual server `auth.sessions` row must bind subject, issuer, session ID, expiry, revocation and actor. Merely decoding a JWT or copying an injected AAL claim is insufficient. |
| `reverifySessions({sessions, signal})` | Recheck the same sessions online and against server rows immediately before timed load. Preserve every session/actor/connection/slot identity and returned order. Return fresh proof fields; do not create replacement identities to hide a revoked/expired session. |
| `openTrustedConnections({kind, count, scopeKey, signal})` | Open independently verified server worker connections needed by the permitted case. Return `kind: trusted`, actual distinct connection IDs, verified service-role/independence and public authority/connection evidence hashes. This method is skipped if a mutation remains uncertain. |

The provider validates each request against `OPERATIONS`, the current installed contract, actual actor capabilities and the exact plan. No arbitrary RPC, SQL, target URL, model endpoint, webhook destination or command body enters this interface. It must ignore none of the scope checks merely because it has service-role access.

## Session and transport evidence

Each Auth descriptor supplies `kind`, `actorLabel`, actual `actorId`, actual unique `sessionId`, assigned `scopeKey` and ordinal (0 for business slots, 0–3 for foreign sessions), distinct `connectionId`, hashes for connection and verification evidence, `onlineAuthVerified`, `serverSessionRowVerified`, matching `serverSessionId`/`serverSessionActorId`, exact issuer/role, `verifiedAt`, `expiresAt`, `revoked: false`, and real `aal`. Runtime approver/executor/billing sessions and load-001 billing-admin require genuine AAL2, a returned verified factor UUID and actual MFA proof. The load-001 billing role is MFA-protected in the actual reviewed bootstrap; other loadBilling roles permit AAL1. Execution races also require two independently authenticated genuine AAL2 executor sessions.

Auth/session proofs must be no older than five minutes and support the remaining 900-second bound. AAL1 claims, stored factor rows, service-role identity or SQL-injected JWT context never substitute for an authenticated MFA session. Multiple authentic sessions for one approved actor are allowed; two tokens for the same session ID are rejected. Private tokens/handles never enter the evidence allowlist.

`call` returns `outcome` in `applied`, `replayed`, `denied`, `empty`, `uncertain`; `responseSha256`, `transportEvidenceSha256`, `originalCommandId` (actual UUID or null for endpoints without caller command IDs), optional actual `entityId`, denial code and optional actual backend span (`startedAt`, `finishedAt`, `backendId`, evidence hash). The identical cached server response may not identify which request applied first, so committed effect counts establish uniqueness; the coordinator does not guess the winning duplicate response.

Client transport overlap and actual backend span overlap are separate fields. Missing backend spans produce null rather than inferred DB lock proof. The standard invitation endpoint accepts only a private token and does not accept a caller command ID. Its public attempt UUID is a correlation identity, not an invented server idempotency input; the real invitation/member/request IDs remain source-bound evidence.

Queries must attribute losing-attempt effects without logging invitation tokens or adding a business audit effect themselves.

## Load and invalid limits

Dispatch uses fixed ten-request blocks (seven indexed reads, two ordinary forecast commands, one bounded analytics snapshot), actual monotonic pacing and at most 2000 inflight requests. Billing-admin has only billing-read access in load scopes and uses `get_wave5_subscription`; other permitted read sessions use source-bound `get_pipeline_forecast`. Commands use fresh command/idempotency identities, and analytics uses the existing scoped `analytics_process_snapshot`. Foreign sessions operate in their own foreign scope and are excluded from mutation selection. All 2000 session IDs and all 500 scopes must appear during measurement.

Requests dispatched during warmup are identified separately at their actual transport start after journal and provider queue delays. The synchronous pre-send hook also measures actual start minus scheduled due time and rejects excess lag using the generator threshold; holding warmup intents cannot produce a catch-up burst. `maximumSchedulerLagMs` and `maximumDispatchLagMs` report distinct evidence. Pre-send failures retain `not-dispatched`, count as scheduled attempts, and do not count as transport sends, warmup samples or measured session coverage. A valid result requires nonempty, rate-bounded warmup, the exact expected paced request count and complete sample/count consistency. P95 is nearest rank over measurement samples only, with strict thresholds under 500ms/1500ms/3000ms. Full request timing includes authority/transport/response verification; separate transport intervals establish overlap. Generator lag, missed duration, limited capacity, any rejection/unknown, incomplete session/scope coverage, a reused command or mismatched committed counts fails the gate. No shortened virtual-time run, single-session sequence or controlled result can set live gates.

The four invalid boundary checks require actual 10001-source, 101-group, 367-day-window and 8MiB-plus-one-byte rejections with zero committed effects. Reviewed per-tenant seeds remain capped (200 opportunities, 800 process events, etc.). The mapped forecast/process APIs accept scopes/time ranges rather than arbitrary source/group/output values. The row boundary cannot fit current caps; group/output fixtures remain unsupported unless the actual approved catalog/projection can produce them. Only the 367-day invalid-window rejection is presently mapped to a feasible request. A missing authorized fixture keeps `invalidBoundaryRejections` and the overall result false, even when separate genuinely executed race/load evidence passes.

An unsupported result is `status: unsupported-under-reviewed-scope`, the exact case/fixture hashes, `noOperationAttempted: true`, `existingScopeOnly: true`, a source-reviewed `fixtureEvidenceSha256` and one fixed reason: `ROW_FIXTURE_EXCEEDS_REVIEWED_CAPS`, `GROUP_FIXTURE_NOT_REVIEWED` or `OUTPUT_FIXTURE_NOT_REVIEWED`. It is recorded with `blocked: true`, `executed: false`, `passed: false`; no response/rejection proof is invented. Additional seed authority would require a concrete scope extension and explicit decision, not inferred permission from the existing bounded scope.

The append-only exclusive `.ndjson` evidence journal persists original intent before each send, barrier readiness/release, actual transport intervals, public identities, committed snapshots, measured samples and final outcome. A crash leaves an incomplete journal, never a rewritten green report. A journal-write failure stops dispatch. Unknown outcomes retain their original identities and reservations for owner-reviewed reconciliation.
