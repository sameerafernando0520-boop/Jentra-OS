# Wave 3 budget and posted-actual variance contract (AC-320)

Status: additive development candidate. `20260925004000_wave3_budgets.sql` is **unapplied**. This contract extends financial statements contract 36 and reuses the Wave 3 scoped command, immutable receipt, audit and outbox engine. It does not change authentication, stock opening or existing journal posting.

## Budget versions

`api.budget_command(tenant, entity, branch, command_id, idempotency_key, client_timestamp, payload, expected_entity_version)` accepts `create`, `save`, `submit`, `approve`, `reject` and `revise`. All commands require entity and selected-branch `finance.budgets.manage`, except decisions require `finance.budgets.approve`. Approval or rejection by the creator or submitter is forbidden. `finance.view` governs read and variance generation. The signed-in actor, not the payload, determines every actor field.

A budget is a versioned, exact-decimal account plan for one legal entity, a year or fiscal period, optional branch, and registered currency. A draft has 1–500 lines referencing active posting accounts. Each line has immutable UUID, account UUID and a nonnegative decimal **string** with at most six fractional digits. JSON numbers are rejected. Contract [46](46_WAVE3_GOVERNED_FINANCIAL_DIMENSIONS_CONTRACT.md) adds governed `cost_centre_id` and `project_id` choices and frozen master versions. Repeated accounts require disjoint dimensional combinations; null means all values, so an overlapping wildcard is rejected. Submission and approval recheck the saved master basis. Without the additive dimension candidate, the original account-only contract still requires null dimension IDs. `reason` is required for every transition. The selected branch can create a branch plan or an entity-wide plan; an entity-wide plan uses `branch_id: null` and only entity-wide dimension masters. A fiscal-period plan must use a period in its budget year.

`create` starts version 1 in `draft`. `save` changes only draft lines and increments optimistic version. `submit` freezes lines for an independent decision. `approve` and `reject` record the decision. Approved/rejected rows and all events are immutable. `revise` names an approved source, requires its exact current version, and creates a new draft under the same root with the next revision. It never rewrites the approved source. Every command has an idempotent receipt, audit event and outbox record; version conflicts are explicit. The desktop stores a single sealed pending command in `budget-version-editor` and replays the identical envelope after uncertain transport or receipt validation.

`api.budget_options` returns up to 50 UUID-ordered versions per page with a cursor. It includes entity-wide and selected-branch versions visible to a caller with `finance.view` at the entity and selected branch. The desktop uses the existing finance account and period pickers and keeps the base currency visible. It never writes directly to budget tables.

## Frozen variance

`api.generate_budget_variance` accepts a new report UUID, an **approved** budget UUID and an as-of date inside its year or fiscal period, no later than today. It requires `finance.view` at entity and selected branch, and expected version zero. For each budget account, only posted journal lines dated from the period start through the cutoff contribute. A branch plan includes only that branch; an entity-wide plan includes all entity branches and therefore requires entity finance access. Normal-balance direction determines signed actuals. When budget currency equals entity base, actuals use posted **base** debit/credit from all transaction currencies; otherwise, only matching transaction-currency journals contribute, using their transaction debit/credit. The report records `currency_basis` to make this rule visible. It performs no FX conversion or journal write.

Budget, actual and `actual - budget` are exact decimal strings. Percentage variance is rounded to six decimals and is null for a zero budget. The saved report freezes its approved revision, account rows, source journal lines, cutoff and summary, so later/backdated postings or budget revisions cannot rewrite it. The dimension candidate filters actuals by frozen governed identities; unassigned historical labels cannot be guessed into a dimension. Generation is idempotent. The desktop uses the separate `budget-variance-editor` encrypted slot for uncertain generation. Bounded attributable CSV/XLSX delivery follows contract [44](44_WAVE3_GOVERNED_REPORT_EXPORT_CONTRACT.md).

`api.budget_variance_reports` lists saved summaries for the **requesting branch only**, 50 per UUID page. `api.budget_variance_page` returns frozen `lines` or `journals`, up to 50 rows per page, with an optional budget-line filter. A selected-branch report cannot be opened from another branch, even by an actor otherwise permitted there. A report supports at most 500 budget accounts, 10,000 source journal lines and 16 MiB of evidence; over-limit generation fails atomically. Direct authenticated table reads/writes remain denied by forced RLS and grants.

## Development proof and acceptance boundary

It proves candidate compatibility and fixture behavior only. It does **not** establish an installed schema, authenticated native walkthrough, real Credential Manager restart, multi-session contention/load or owner signoff. The stock-opening acceptance records and authentication are outside this candidate.
