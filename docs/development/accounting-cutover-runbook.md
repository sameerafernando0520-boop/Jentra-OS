# Accounting cutover and first close

Use this runbook for each legal entity, with each branch covered by its own opening batches. Finance owns the signed opening totals and first-close acceptance. The release owner records the reviewed app revision, installed migration manifest, artifact hashes and target. Confirm the opening workflow and scopes on that exact release before loading company records.

## Release and activation prerequisites

1. Rehearse the [additive SQL candidate](../../supabase/candidates/20261104090000_finance_opening_import.sql) on the isolated restore. Apply the reviewed candidate only to the approved target with the matching migration baseline and recovery plan.
2. Compile the matching desktop client with `--dart-define=FINANCE_OPENING_IMPORT_ENABLED=true`, or use the [governed Windows build](../../tools/desktop-release/README.md) with `-EnableFinanceOpeningImport`. The governed build records the feature configuration in its source identity and release manifest. Deploy and test that build against the candidate APIs and the selected entity and branch before posting any company records.
3. Assign scoped `finance.openings.view`, `finance.openings.prepare`, `finance.openings.approve` and `finance.openings.post` according to each role's duties. Confirm the preparer cannot approve their own submission, revoked access is denied and only the designated poster can post an approved batch. Confirm successful MFA with the actual actors.

## 1. Prepare and reconcile the source

- Approve the opening cutoff, first-close date, legal entity and branches, base and transaction currencies, posting periods, tax configuration, account and party mappings, document sequences and equity opening-clearing accounts. Configure dated cash-flow mappings for cash/bank and other moving balance-sheet accounts. Assign separate scoped preparer and approver accounts. Verify both can sign in with MFA and that unrelated branches are denied.
- Freeze the legacy snapshot at the cutoff. Retain the signed trial balance by account, customer and supplier ageing by document and currency, bank balances and statements, stock quantity and valuation with locations and tracking IDs, and fixed-asset cost and accumulated depreciation schedules. Record outstanding bank items and tax control balances separately. Record source filenames, hashes and signoff in the restricted cutover evidence folder.
- Reconcile the legacy AR/AP ageing, stock, bank and asset schedules to the signed trial balance before import. For each outstanding AR/AP document, keep its stable source key, party code, reference, original document and due dates, signed remaining transaction amount and carrying base amount at cutoff. Keep credits and partially settled documents distinct. Group files by branch, Customers or Suppliers, and transaction currency. Use the workspace template and retain the original extracts privately.
- Take an approved backup and prove it restores to an isolated target. Compare ledger totals, open items, stock, fixed assets, and required attachment bytes and hashes. Record the recovery owner and the point beyond which a production restore would discard valid activity. Rehearse the remaining steps on the isolated target before live posting.

On the frozen source and isolated restore, run [accounting-cutover-restore-check.sql](accounting-cutover-restore-check.sql) with the same tenant, legal entity and cutoff. Use a backup operator with full read visibility and retain both JSON results privately. Compare the exact ledger and account totals, dated AR/AP groups and all 20 dataset row counts and SHA-256 fingerprints. The fingerprints cover all entity history, including rows after cutoff; the totals and ageing use the cutoff. `captured` means the query finished and returned complete residuals. It does not mean a second target matched. Stop on an invalid scope, incomplete residual, SQL error or difference. Compare Auth, audit history, configuration, Storage metadata and actual private attachment bytes separately; this accounting subset cannot establish their restoration.

For a disposable synthetic rehearsal, run `node tools/accounting-cutover/rehearse.mjs` from the candidate checkout with the pinned PGlite runtime installed. It accepts no target or file arguments, loads the reviewed opening/reversal fixtures, exports a compressed database image in memory, restores a new database, and checks 27 table fingerprints, exact ledger totals, four dated accounting snapshots for every populated opening entity, scoped API reads and access denials. It retains no archive and simulates Auth/Storage. Its approved-fixture hash guard requires review if the opening runner changes. Asset, bank-statement and Storage object-byte recovery still need populated acceptance; their empty fingerprints establish only empty-table preservation. A successful synthetic rehearsal supplies development evidence; the approved company backup and attachment restore remain separate acceptance requirements.

## 2. Check reporting capacity

Run [accounting-cutover-capacity.sql](accounting-cutover-capacity.sql) in a fresh SQL session against the approved isolated restore using a database operator account with access to the listed tables and `finance.flow_residual`. Fill every value in its single input row. Enter zero for a reviewed category with no additional rows. Forecast only rows that the target does not already contain. `opening_ar_ap_items` is the total unposted document count across all batches in the legal entity. Enter opening journals from other workflows as line counts and forecast the line count from day-one transactions and first-close adjustments through `first_close` separately. Include new posting accounts only if absent from the restored chart.

The SQL uses one read-only snapshot and returns aggregated counts. It counts cumulative posted lines across all entity branches because the statement builder does the same. Each AR/AP opening item adds two lines. Resolve missing scope or invalid inputs and any count above 10,000 journal lines or 5,000 posting accounts before cutover. Keep signed planning estimates and headroom with the result. Recompute after rehearsal using observed counts and only the remaining unposted forecast.

For each cutoff and first-close branch and foreign currency that requires FX revaluation, add projected additional residual documents to the observed count in `observed_fx_groups`. Include new groups with an observed count of zero. Investigate any projection above 1,000. Statements also have a 16 MiB snapshot limit, and FX snapshots have a 4 MiB limit. Generate the four statements with the agreed comparative periods and the FX snapshots on the populated isolated target to verify those evidence limits, timings and source drill-through. Validate AR/AP control, tax, inventory and governed exports separately using company-volume data. A count check establishes headroom for the specified counts. The populated rehearsal and signed results establish the first-close gate.

### Local capacity fixture

An isolated PGlite database exercised the preflight using the repository's `finance.flow_residual` function. The sample dates, 31 October and 30 November 2026, are planning inputs for the count query. The transaction confirmed `transaction_read_only = on`.

- Seed two posted lines through the cutoff in different branches of one legal entity, and one more through first close. Add one draft line, one after first close and one for another entity. Seed 4,999 posting accounts, one nonposting account and one other-entity account. The result counts two cutoff lines, three first-close lines and 4,999 accounts.
- Enter 4,998 planned AR/AP documents, zero other opening lines, one post-cutoff line and one new posting account. The result projects 9,998 cutoff lines, 10,000 first-close lines, 5,000 posting accounts and zero line headroom. Increasing either the post-cutoff line or account input by one returns `exceeds_count_limit`. Missing or unknown scope, negative inputs and reversed dates return `invalid_or_inaccessible_scope_or_inputs`.
- In an LKR entity, seed a USD 25 item carried at LKR 7,500 and allocate both amounts in full at first close. In a second branch seed a GBP item with zero transaction residual and LKR 1 carrying residual. Seed a local LKR 25 item. The FX result shows one USD and one GBP item at cutoff, and only the GBP item at first close. Equal dates with zero post-cutoff lines return one set of FX groups.

## 3. Load opening balances

1. From Finance, open **Opening balances** in the intended company and branch. Select Customers or Suppliers, cutoff, transaction currency, source system and the reviewed control and equity clearing accounts. Choose the CSV or Excel file. Review every row issue, the document count, outstanding amount and carrying base total against the signed extract. Correct source errors and preview again.
2. Save the draft and submit it for review. The independent approver checks the saved evidence and approves the exact batch. Post explicitly and verify the posted status, document count and linked source, open-item and journal references. Record batch identifiers and reconcile by branch, currency and party before proceeding to the next batch.
3. Use governed stock and asset opening workflows where applicable. Enter remaining approved opening trial balance lines through the governed finance workflow. Exclude AR/AP, stock, asset or other control postings already supplied by their respective opening workflows. Reconcile any opening-clearing balance to zero once all opening entries post. Match bank book balances and outstanding items to statement evidence.
4. At cutoff, reconcile the opening trial balance and retained earnings, AR/AP ageing and controls, bank, stock quantities/valuation and assets against signed legacy records and GL. Investigate differences to their source. Obtain preparer, independent approver and Accounts owner evidence before releasing day-one operations.

If acknowledgement is lost, use **Retry saved request** in the same actor and company/branch scope. Preserve the original command and check the recorded batch status and posted references. Pause the next batch while an outcome or discrepancy remains unresolved.

### Reverse an unused posted batch

Install the reviewed follow-on opening-reversal candidate with the matching client before using this workflow. Assign `finance.openings.reverse` to the designated reversal poster. Preparation and review use the existing scoped opening permissions and MFA. Keep requester, original preparers and independent reviewer distinct.

1. Reconcile the incorrect original batch and retain its source evidence. The reversal path accepts a batch with no allocation history, FX-run participation or active supplier payment selection. Prior allocation history remains a blocker even if that allocation was reversed.
2. Open the posted batch and choose **Request reversal**. Enter the approved reason and posting date. Use an open period on or after the original cutoff and no later than today. Foreign-currency batches must use their original fiscal period. Review the original source, exact amounts and proposed date with the independent reviewer.
3. The reviewer approves the frozen request. The designated poster explicitly posts the reversal. If a period, account, permission or source dependency changes, refresh and resolve the refusal before proceeding. A pending or approved request can be cancelled. Rejected and cancelled requests remain in history.
4. Verify the posted reversal, every original-to-counter source link, opposite journal and protected allocation. Reconcile both AR/AP controls and opening clearing with the approved correction. The original and counter-items have zero remaining amount after reversal, and earlier as-of reports retain the original balances.

The original batch, journals, items and source keys remain immutable. A corrected replacement uses a separately reviewed import with a new stable source key, retaining the original batch and reversal references with the signed source records. Settlement or FX history requires a separately reviewed correction outside this unused-batch path. The ordinary allocation-reversal workflow cannot undo a system allocation created by opening reversal.

Each reversed document adds two journal lines. Include those lines and any replacement imports in the capacity forecast and generate fresh statements after the correcting entries. Existing report snapshots retain their as-generated content.

## 4. Close and sign off the first period

Rehearse and then verify representative sales invoices, customer receipts and allocations, purchases/receipts/supplier bills/settlements and a return, inventory and GRNI effects, an approved manual journal and linked correction, and bank statement import and reconciliation. Run AR/AP and inventory control tie-outs, tax review and FX with independent review of exceptions. Generate trial balance, profit and loss, balance sheet and cash flow and verify comparative totals, source drill-through and downloadable evidence. Confirm the period-close controls and signoff with the designated Accounts owner.

Record target, release/migration identifiers, entity and branches, cutoff and first-close dates, source/backup references, opening batch and report IDs, signed reconciliations, capacity results, exceptions, timestamps and the preparer, approver, Accounts owner and release owner. Keep actual source records and evidence in the approved restricted location.
